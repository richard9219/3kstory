## 里程碑 1：第三方视频平台接入 & 解说视频能力

### 一、目标概述

- **平台接入**：在官网完成抖音 / 小红书 / B 站 / 微博四个平台的账号绑定，为后续「一键发布」打通账号层能力。
- **官网看板**：在官网提供登录后的「运营看板」，聚合 4 个平台及内部生成数据，帮助用户查看内容表现。
- **解说视频能力**：实现「电影/电视解说」类型的 AI 视频生成流程（从解说文案到成片），为后续短剧与长片能力打基础。

---

### 二、官网看板 + 登录 + 平台绑定

#### 2.1 用户与会话管理

- 当前后端已经有 **用户体系 + JWT**：
  - 注册 / 登录接口；
  - 中间件基于 `Authorization: Bearer <token>` 做鉴权；
  - 前端用 Zustand + localStorage 持久化 token。
- **里程碑 1 保持 JWT 模式不变**：
  - 所有需要登录才能访问的接口（如看板、平台绑定）都用现有中间件保护；
  - 若用户未携带有效 token，前端根据 401 跳转到首页/登录。
- 后续如需更安全的 Session（httpOnly Cookie + 服务端会话），可在后续里程碑调整，但不作为里程碑 1 必须项。

#### 2.2 平台绑定（在官网完成）

- 绑定入口：网站内固定使用 `/platforms` 页面作为平台账号管理中心。
- 后端：已提供统一的平台 OAuth 流程：
  - `GET /api/v1/platforms/configured`：返回当前环境实际配置了 OAuth 的平台列表（如 `["bilibili","weibo"]`），前端可据此显示「暂未开放」。
  - `GET /api/v1/platforms/:platform/authorize`：返回对应平台的授权链接，前端重定向跳转。
  - `GET /api/v1/platforms/:platform/callback`：OAuth 回调；用 code 换 token + 拉取用户昵称/头像，保存到 `platform_accounts` 表后重定向到前端结果页。
  - `GET /api/v1/platforms`：当前用户已绑定的平台账号列表。
  - `DELETE /api/v1/platforms/:platform`：解绑。
- 前端：
  - `/platforms` 展示 4 个平台卡片，状态包括：
    - 未配置（后端未设置 ClientID/Secret）：按钮为「暂未开放」，说明文字提示。
    - 可绑定但未绑定：显示「绑定」，点击走 OAuth 流程。
    - 已绑定：展示平台头像 + 昵称 + 解绑按钮。
  - `/platform-bound`：承接 OAuth 回调的结果页，根据 `ok` / `err` 查询参数显示绑定成功/失败。

#### 2.3 运营看板设计

- 新增前端页面 `/dashboard`（登录后访问）：
  - 顶部 **总览卡片**：总作品数、总播放量（内部统计）、总点赞/互动（后续对接平台数据）。
  - 中间 **平台卡片区域**：
    - 每个平台一张卡片：绑定状态、平台昵称/头像、关键指标（如作品数、估算播放量）。
    - 从卡片进入对应平台的详情页（可在后续里程碑扩展）。
  - 下方 **最近记录列表**：近期生成/发布的视频记录（平台、标题、状态、时间）。
- 后端需要提供的接口（里程碑 1 版本可先只返回内部数据）：
  - `GET /api/v1/analytics/summary`：返回按用户聚合后的「内部运营指标」与已绑定平台列表。
  - `GET /api/v1/analytics/videos`：返回当前用户的生成/发布记录列表。
- 数据源：
  - **内部数据（必做）**：
    - 在生成视频/发布视频时写入 `video_tasks`、`publish_records` 等表，形成自己的业务日志和统计基础。
  - **平台数据（可选，逐步增加）**：
    - 利用各平台的开放接口拉取粉丝数、作品数据等，结果做缓存 / 日汇总入库。
    - 在里程碑 1 初版中，可以只展示「内部生成/发布次数」，平台侧深度指标可留给后续里程碑实现。

### 三、后端数据库选择与使用

#### 3.1 是否需要数据库

- **必须要有数据库**。里程碑 1 依赖持久化的数据包括：
  - 用户、项目、场景、AI 任务（已有模型）；
  - 平台账号绑定信息（`platform_accounts`）；
  - 视频生成任务（`video_tasks`，可在现有 `AITask` 基础上扩展或新增表）；
  - 发布记录与后续运营指标（`publish_records`、`platform_metrics_daily` 等）。

#### 3.2 Postgres vs MySQL

- 当前实现：使用 **PostgreSQL + GORM**。
- 如果业务要求强烈偏向 **MySQL**，迁移方式：
  - GORM 本身支持 MySQL，只需：
    - 改用 `gorm.io/driver/mysql` 与 MySQL DSN；
    - 将部分 `JSONB` 字段调整为 MySQL 的 `JSON` 类型；
    - 重新初始化数据库与迁移。
- 里程碑 1 建议：
  - 若当前项目仍在早期、尚未上正式环境，可评估一次性切换到 MySQL；
  - 若已经基于 Postgres 跑通多处功能，**优先保证功能交付**，数据库迁移可延后到后续里程碑统一规划。

### 四、「电影/电视解说」AI 视频生成方案

目标：在里程碑 1 内，做出一条相对轻量、但完整可用的「解说类视频」生成链路，为后续短剧 / 长片能力打基础。

#### 4.1 用户业务流程

1. 用户在官网选择「创建解说视频」：
   - 填写：电影/电视剧名称、可选剧情简介 / 链接、解说风格（搞笑 / 深度分析 / 情感向等）、目标时长。
2. 系统执行解说生成流程：
   - AI 生成解说提纲与分段文案；
   - 对每一段调用 TTS 生成语音；
   - 使用模板化画面（背景 + 大字标题 + 字幕）或简单图片；
   - 利用 ffmpeg / 本地视频服务合成出一条完整视频（16:9 为主，预留 9:16 支持）。
3. 生成完成后：
   - 结果写入视频任务表；
   - 在看板和项目详情里展示该解说视频；
   - 未来可以通过绑定平台进行分发（M1 先打通账号层和生成层）。

#### 4.2 关键技术设计

1. **解说文案生成（AIService 扩展）**
   - 在现有 `GenerateScript` 能力上增加「解说模式」的 prompt 模板，例如 `GenerateNarrationScript`：
     - 输入：影片信息（名称、简介）、风格、目标时长。
     - 输出：分段 JSON 结构，每段包含：
       - `title`（小标题）；
       - `narration_text`（完整旁白文本）；
       - `estimated_duration`（预估时长）。
   - 可以沿用当前的 JSON Schema，以便前端/后端统一处理场景结构。

2. **TTS（文字转语音）**
   - 引入一个可用的 TTS 服务（阿里云 / 火山 / OpenAI TTS 等），封装成 `TTSService`：
     - 接口：`Synthesize(text, voice, speed) -> 音频文件 URL 或路径`。
   - 结合现有本地服务架构：
     - 可将 TTS 调用与合成逻辑都放入本地视频服务，主服务只负责任务编排与状态管理。

3. **画面生成（M1 使用模板，不强依赖 Runway/Pika）**
   - M1 版本优先实现**模板化画面**：
     - 背景：统一渐变/动画背景（例如你已有的本地 video service 输出），或指定封面图；
     - 文本：将每段的标题与关键句以大字形式展示，同时在底部输出字幕；
     - 好处：实现成本低，完全可控，能尽快跑通全链路。
   - 后续（M2+）再用 Runway/Pika 生成更丰富的镜头：
     - 将每一段的描述送入 Runway/Pika，生成 3–10 秒片段；
     - 最终用 ffmpeg 拼接成完整解说视频。

4. **合成与任务管理**
   - 扩展现有本地视频服务（`cmd/local-video-service`）：
     - 新增「解说模式」的生成接口：接收解说分段 JSON + 对应音频文件列表 + 模板配置，输出完整 mp4；
     - 保持与当前 `/v1/generate` 风格一致，便于切换 provider。
   - 在主后端中：
     - 为解说任务增加单独的 TaskType（如 `narration_video`）；
     - 在 `POST /api/v1/projects/:id/generate-narration` 中触发完整流程（AI→TTS→合成），并通过现有 `AITask`/`VideoTask` 体系跟踪状态。

#### 4.3 与平台接入和看板的关系

- 平台绑定：为解说视频 **后续分发** 做准备；里程碑 1 优先打通绑定与生成，发布 API 可以在 M1 后半段/M2 中逐步接入。
- 看板：可以在解说任务落地后，优先展示**内部维度**：
  - 用户已创建的解说视频数量、最近生成时间等；
  - 后续再叠加「已成功发布到各平台的视频数」与平台真实数据。

---

### 五、小结

- 里程碑 1 不仅要完成四大平台的账号接入与绑定，还要在官网内提供登录后的运营看板，让用户可以管理平台账号并看到基础数据。
- 后端必须依赖数据库持久化，当前使用 PostgreSQL，保留未来迁移到 MySQL 的可能，但不影响里程碑 1 的交付。
- 在视频能力上，里程碑 1 将实现一条从「解说文案 → TTS → 模板化画面 → 成片」的完整链路，为后续短剧与电影级视频生成打基础。
